# FinBonds Ratings Skill

Кредитные рейтинги в fin_bonds: гейт свежести, наполнение командой
`update-ratings` (скоупы portfolio/missing/catalog — задача 002.9), правило
«стоит ли ещё обновлять», интерпретация национальных шкал трёх агентств.

## When to Use

- «Обнови рейтинги» — один прогон по SOP ниже (не по всему каталогу, а
  скоупом по запросу).
- Вопросы «какой рейтинг у X», «почему риск 1 при рейтинге A-»,
  «рейтинг понизили», «устарели ли рейтинги».
- Перед включением бумаги в кандидаты на покупку — проверка рейтинга
  эмитента (для бумаг вне портфеля рейтинг добирается скоупом `missing`).

Don't use for: risk_level Т-Банка сам по себе (это поле БД, не рейтинг
агентства); массовых алертов по изменениям — `finbonds-risk-monitoring`
(`check-changes` читает `rating_history`).

## Prerequisites

- Контракт путей и хоста — см. `finbonds-ops` (CLI на хосте, psql через
  `"${FIN_BONDS_PSQL:-psql}"`).
- Гейт свежести — скрипт этого скилла `scripts/ratings_freshness.sql`
  (`"$FIN_BONDS_SKILLS_DIR/finbonds-ratings/scripts/ratings_freshness.sql"`).
- Ночная автоматизация: шаг 4 `run_update.sh` = `update-ratings` без
  флагов (скоуп `portfolio`). Ручной запуск безопасен: запись в
  `rating_history` идемпотентна за день (уникальный индекс
  `isin+rating_date+rating_code`, миграция 012) — дублей не будет.

## How to Run

Гейт свежести (миллисекунды):

`"${FIN_BONDS_PSQL:-psql}" --csv -f "$FIN_BONDS_SKILLS_DIR/finbonds-ratings/scripts/ratings_freshness.sql"`

Колонки (CSV, одна строка): `rating_history_rows|max_rating_date|na_tail|never_checked|alive_catalog`, где `na_tail` — живые бумаги каталога с последней проверкой `'N/A'`, `never_checked` — живые без проверок вовсе.

Запуск обновления (хост):

`ssh ${FIN_BONDS_HOST} 'cd ${FIN_BONDS_APP_DIR:-$HOME/work/bonds} && venv/bin/python main.py update-ratings --scope portfolio'`

## Procedure

1. **Гейт свежести** — прогони скрипт выше. Критерий решения — шаг 2.
2. **Правило «стоит ли обновлять»:** рейтинги обновлялись < 2 дней
   (`max_rating_date` = сегодня/вчера) **и** `na_tail + never_checked`
   не растёт → обновление не требуется, сообщи гейт-числа и остановись.
   Повторный прогон идемпотентен — вреда нет, но и смысла тоже.
3. **Выбор скоупа по запросу:**
   - «обнови рейтинги» (без уточнений) → дефолтный `--scope portfolio`
     (бумаги портфеля, полный набор адаптеров мониторинга);
   - «дозаполни рейтинги / убери N/A» → `--scope missing --limit 200`
     (живые бумаги каталога с последней проверкой `'N/A'` или без
     проверок; только `credit_rating`);
   - «весь каталог» → `--scope catalog` — разовый бэкфилл ~1.5-2 тыс.
     бумаг при `--delay 0.5`: `timeout` ≥ 3600, **не запускать рядом с
     ночным окном таймера** (`flock` защищает только `run_update.sh`,
     не саму команду).
   - Одна бумага по имени/ISIN → `--isin <ISIN>` (работает и вне
     портфеля; скоуп игнорируется).
4. **Запусти** команду хоста (см. How to Run, подставь скоуп/флаги) и
   прочитай итоговую сводку в конце stdout:
   `Итог: scope=<...>; checked=N; rated=N; na=N; errors=N`.
5. **Верификация** — повторный гейт: `rating_history_rows` и
   `max_rating_date` продвинулись (после `portfolio`/`missing` прогона),
   `na_tail` сократился. Покажи пользователю `count(*)` и
   `max(rating_date)` из гейта, а не только сводку команды.

## Интерпретация (ответы про рейтинг)

**Источники в БД:** провайдеры опрашиваются по порядку moex (ISS
`/iss/cci/rating` — рейтинги всех агентств, в логе есть имя агентства)
→ дополнительные провайдеры, если подключены (только код). Имя агентства в БД НЕ хранится (колонки
`agency` нет) — не выдумывай его для записей из `rating_history`;
агентство конкретного рейтинга подтверждай пресс-релизом
(`finbonds-web-verify`).

**Шкалы (национальные, лучшая слева):** AAA > AA+ > AA > AA- > A+ > A >
A- > BBB+ > BBB > BBB- > BB ... Всё выше BBB- — инвестиционный уровень.
Суффиксы: `(RU)` — АКРА, `ru…` — Эксперт РА, `.ru` — НКР. Рейтинги разных
агентств не усреднять и не складывать в одну букву — показывать все с
суффиксами шкал.

**Маппинг к `risk_level` Т-Банка (эмпирический, уточнять по каталогу):**
risk 1 ≈ AA- и выше плюс верхняя часть A-диапазона (A+, A, A-); risk 2 ≈
BBB+ … BB+; risk 3 ≈ BB и ниже / листинг 3.

**«Рейтинг низкий?»:**
1. Назвать уровень + прогноз + дату + агентство (из свежего пресс-релиза).
2. Позицию на шкале словами («седьмая ступень из ~20, инвестиционный
   уровень»). «A-» — полноценный инвестиционный уровень, а не «низкий».
3. Историю по `SELECT rating_date, rating_code FROM rating_history WHERE
   isin = '...' ORDER BY rating_date` — когда присвоен, когда менялся.
4. Связь с доходностью: понижение внутри инвест-диапазона = премия в
   купоне, а не близость дефолта.
5. Что мониторим дальше: понижения, негативный прогноз, отзыв рейтинга —
   триггеры `finbonds-risk-monitoring`.

**Понижение/прогноз:** даунгрейд ниже инвестиционного порога (BBB-) —
critical-событие; любой даунгрейд — high (пороги — `finbonds-risk-monitoring`).
Пресс-релиз важнее агрегатора: у агрегаторов бывают чужие серии и старые
уровни.

## Pitfalls

- `'N/A'` не пишется в `rating_history` (норма, не дефект): код вне шкалы
  `rating_scale` остаётся только в `monitoring_checks` — «пустоты» в
  `rating_history` при живом N/A в `monitoring_checks` не чинят SQL-ом.
- Колонки `agency` в БД нет — агентство для исторической записи не
  выдумывать (см. Интерпретацию).
- Первый прогон `missing` ≈ полный каталог (у большинства живых бумаг
  проверок ещё не было) — это ожидаемо; дозировать `--limit 200`.
- Погашенные бумаги (`maturity_date < CURRENT_DATE`) из скоупов
  `missing`/`catalog` исключены.
- `flock` есть только у `run_update.sh` — длинный catalog-прогон не
  совмещать с ночным окном (параллельный запуск возможен).
- Квоты: на каждую бумагу 2–3 внешних запроса; не уменьшай `--delay`
  без необходимости (недокументированный `/cci`, лимиты источников).
- Telegram-уведомления шлются только скоупу `portfolio`/`--isin`;
  `missing`/`catalog` пишут в БД молча (anti-spam) — не жди сообщения.
- Отсутствие рейтинга у эмитента ≠ плохой рейтинг; но бумагу без
  рейтинга нельзя называть «надёжной» — только `risk_level`/листинг.

## Verification

- Сводка `Итог: scope=...; checked=...; rated=...; na=...; errors=...`
  присутствует в выводе команды; числа согласуются с гейтом до/после.
- В ответе пользователю названы `count(*)` из `rating_history` и
  `max(rating_date)`; после прогона дата — сегодняшняя.
- Для интерпретационных ответов: агентство, уровень, прогноз, дата
  пресс-релиза подтверждены веб-проверкой (не только БД).
