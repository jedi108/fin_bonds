# README_SKILLS_HERMES — конвенция скиллов Hermes и синхронизации с профилем

Портативный документ: живёт в проекте рядом со скиллами, копируется в другие
проекты как есть. Проект-специфичное — только значения в §0; имена в примерах
взяты из проекта-родителя (fin_bonds) и заменяются на свои. Каждое правило
появилось после реального инцидента — не удаляй «очевидные» пункты.

## 0. Карта окружения (заполняется под проект)

| Сущность | Значение (пример) |
|---|---|
| Hermes-хост (ssh) | `user@hermes-host` |
| Docker-стек Hermes | `/home/<user>/hermes` (compose: базовый файл + override скиллов) |
| Контейнер агентов | `hermes-ai` (s6-overlay; сервис `gateway-<профиль>` на каждый профиль; uid `hermes`) |
| Данные Hermes (в контейнере) | `/opt/data` (= `<стек>/data/hermes` на хосте, общий rw) |
| Профиль агента проекта | `/opt/data/profiles/<profile>/` |
| Каталог скиллов профиля (в контейнере) | `/opt/data/profiles/<profile>/skills/<категория>/` |
| Каноническое дерево скиллов (git) | репозиторий проекта, `<repo>/skills_hermes/<категория>/` |
| Манифест | `skills_manifest.yaml` рядом с деревом |
| Враппер доступа к данным из скиллов | `/opt/data/profiles/<profile>/bin/<tool>.sh` |
| Команды | `make deploy-skills` / `make check-skills-profile` |

## 1. Модель рантайма — знать до любых правок

1.1 **Все профили агентов живут в ОДНОМ контейнере.** s6 запускает
`gateway-<профиль>` для каждого профиля, все процессы под одним uid
(`hermes`), `/opt/data` смонтирован rw и общий. Следствие: изоляция между
профилями на уровне docker или прав доступа невозможна. Если данные проекта
не должны быть видны чужим агентам — их не должно быть в контейнере вообще:
маунты и env у контейнера одни на всех (см. §9).

1.2 **Конфигов два уровня:** глобальный `/opt/data/config.yaml` и профильный
`/opt/data/profiles/<p>/config.yaml`. Часть ключей (в т.ч. `skills.*`)
читается только из глобального; мусор в профильном может быть неэффективным,
но живёт вечно и путает при разборе — чистить миграциями, не надеяться на
«он и так не работает».

1.3 **Секреты профиля грузятся в secret-scope, а не в процесс.** Hermes
читает `<profile>/.env` в свой python-scope (`get_secret`) для внутренних
нужд (токены ботов, модели). Процессное окружение — `os.environ`, а значит и
env terminal-команд агента — это только env контейнера. Отсюда правило §2.4.

1.4 **`/opt/data` принадлежит uid контейнера**, пользователь хоста не может
читать/править профильные файлы напрямую. Все правки — через `docker exec`
(внутри root) с выравниванием владельца по каталогу профиля
(`stat -c %u:%g <skills_root>`).

1.5 **Список скиллов строится на старте сессии и кэшируется**; содержимое
скилла читается с диска при каждом `skill_view`. Возобновлённая
(`--resume`) сессия продолжает видеть старый индекс: «задвоения» и
«пропажи» после деплоя в живой сессии лечатся **новой сессией**, а не
правками инфраструктуры. Не давать агенту «чинить» самому (переименования,
правки файлов) — источник правды один, git-дерево.

## 2. Железные правила доставки скиллов

2.1 **Канал доставки один — синк профиля** из канонического git-дерева
(скрипт синка + манифест, §3–4). Никаких ручных копий в профиль.

2.2 **`skills.external_dirs` запрещён** — ни в глобальном, ни в профильном
конфиге. Регистрация внешнего каталога дублирует каждый скилл, и
`skill_view` отказывается выбирать: «Ambiguous skill name: 2 skills match
across your local skills dir and external_dirs. Refusing to guess». Агент
тратит попытки и уходит читать файлы напрямую. Лекарство — убрать
регистрацию и маунт, а не «переименовать дубль».

2.3 **Маунт дерева скиллов в контейнер запрещён.** Это второй физический
экземпляр скиллов в контейнере (и он читаем всеми профилями). Скилл
самодостаточен: скрипты лежат внутри каталога скилла и попадают в профиль
синком.

2.4 **Секреты: не в env контейнера, не дословно в командах, не в промптах.**
Хранилище — `<profile>/.env`. Доступ из команд — через враппер:

```sh
#!/bin/sh
# Враппер <tool> профиля <p>: source профильного .env и exec <tool>.
set -a                                     # ОБЯЗАТЕЛЬНО (см. ловушку ниже)
. /opt/data/profiles/<p>/.env
set +a
exec <tool> "$@"
```

Ловушка: `. file` без `set -a` создаёт shell-переменные, но НЕ экспортирует
их — целевая программа (libpq, клиенты API) их не увидит. Симптом:
«connection to server on socket /var/run/postgresql failed» при живых
значениях в файле.

2.5 **Пути в командах скиллов — абсолютные, внутрь профиля:**
`/opt/data/profiles/<p>/skills/<cat>/<skill>/scripts/x.sql`. cwd
terminal-команды не гарантирован; относительные пути — источник «No such
file or directory».

2.6 **Правки скиллов — только в дереве (git).** Профильная копия
перезатирается синком; правка профиля руками — потерянная работа.

2.7 **Деплой — штатный шаг процесса:** правка → validate → commit/push →
`make deploy-skills`. Не откладывать и не деплоить руками (ssh+sed/scp) —
ручные правки не проходят миграции и проверки, а следующий деплой их
сотрёт или задублирует.

## 3. Манифест skills_manifest.yaml

- `canonical.skills` — канонический набор. Новый скилл добавляется
  **одновременно** с созданием каталога: валидатор проверяет
  дерево↔манифест, любое расхождение валит деплой (`TREE-FAIL`) до всякой
  записи в профиль.
- `retired` — скиллы к удалению из профиля. Удаление **только** через этот
  список (синк делает rm -rf). Последовательность: перенести уникальный
  контент в дерево → удалить каталог → перенести имя из `canonical.skills`
  в `retired`. Удаление «просто каталогом» оставит копию в профиле (в
  отчёте — `EXTRA`).
- `profile_only_allowed` — черновики, существующие только в профиле
  (созданы самим агентом). Синк их не трогает (`LEAVE_ALLOWED`), check
  информирует. Портировать в дерево или удалять по мере созревания.
- Формат SKILL.md: frontmatter `name / description (≤60 симв., с точкой) /
  version / author / license / platforms`, секции When to Use /
  Prerequisites / How to Run / Procedure / Pitfalls / Verification; без
  машинных путей кроме профильных (§2.5) и имён переменных враппера.

## 4. Семантика синка (что произойдёт при деплое)

- Сравнение по **хешам всех файлов скилла** (не только SKILL.md):
  `SKIP` (идемпотентный no-op) / `UPDATE` (замена каталога целиком) /
  `INSTALL` / `REMOVE`.
- После реальной записи — **самопроверка** (остаточный дрейф = exit 2); в
  конце деплоя — `check` (exit 1 при любом расхождении). «Наполовину
  применённый» деплой невозможен: либо всё зелёное, либо падение с отчётом
  (MISSING/STALE/RETIRED/EXTRA/TREE-FAIL).
- Итого контракт: **обновить** = править дерево; **добавить** = каталог +
  строка в `canonical.skills`; **удалить** = минус каталог + имя в
  `retired`; черновики агента — в `profile_only_allowed`, иначе не трогать.

## 5. Гигиена контейнера — миграции внутри deploy-скрипта

- Все правки конфигов/профиля — **идемпотентные шаги deploy-скрипта**, не
  ручные ssh-правки: нет паттерна — no-op; есть — бэкап `.bak-<timestamp>`
  → правка → верификация → marker-файл.
- **Рестарт контейнера — только при реальном изменении конфигов**
  (marker-файл): рутинный деплой скиллов не должен ронять сессии живого
  бота.
- `tar`-перенос сохраняет mtimes — **дрейф детектить хешами, не датами
  файлов** (mtime профильной копии = время доставки (rsync) на хост, не время
  записи).
- Деплой без зелёной диагностики (§7) считается несостоявшимся.

## 6. Cron-промпты (jobs.json профиля)

- Это **живые данные вне git**; правятся только идемпотентной миграцией
  deploy-скрипта (python json + бэкап).
- **Урок: миграция «одним replace» недостаточна.** В промпте меняется и
  инструмент (например `psql "$DSN"` → враппер), и все машинные пути (маунт
  удалён → путь в никуда). Заменять полные команды; в диагностику — guard
  «в промптах не осталось старых путей»: иначе неполная миграция ловится
  только падением по расписанию.
- Ранняя проверка миграции — **ручной прогон**: `hermes -p <profile> cron
  run <job-id>`; дедуп-правила внутри промпта (last_alert_*) предотвращают
  двойные отправки при преждевременном пуске.
- После миграции сверять фактическое выполнение
  (`cron/output/<job>/<ts>.md`): команды в транскрипте должны быть новыми.

## 7. Диагностика деплоя (минимальный набор guard'ов)

- `external_dirs` отсутствует в глобальном И профильном конфигах;
- env контейнера не содержит секретов проекта (`grep POSTGRES_/PG*` и
  аналоги);
- cron-промпты без старых машинных путей;
- YAML обоих конфигов валиден;
- профильные скиллы и их скрипты читаемы по новым путям;
- враппер работает (тривиальный запрос к БД/сервису через него);
- границы: `.env` хоста недоступен из контейнера (проверка под uid
  `hermes`, а не root — root всё читает).

## 8. Грабли: симптом → причина → действие

| Симптом | Причина | Действие |
|---|---|---|
| `skill_view`: «Ambiguous skill name: 2 skills match» | скилл виден дважды (профиль + external_dirs) | убрать external_dirs + маунт; новая сессия |
| В списке скиллов дубли | то же | то же |
| psql: «connection to server on socket /var/run/postgresql failed» | враппер без `set -a`; креды не попали в env процесса | `set -a` вокруг source `.env` |
| «No such file or directory» на скрипт скилла | путь на удалённый маунт или относительный | абсолютный путь внутрь профиля |
| Деплой упал `TREE-FAIL` | дерево и манифест разъехались | каталог + строка в манифесте одновременно |
| `check`: `EXTRA <skill>` | скилл удалён из дерева без `retired` | имя в `retired`, переразвернуть |
| Агент после деплоя видит старый список | кэш индекса сессии | новая сессия (содержимое обновится и так) |
| Агент «чинит» сам — переименовывает/правит скиллы | stale-индекс + инициатива | отозвать; правки только через дерево; новая сессия |
| Рутинный деплой уронил сессии бота | безусловный restart | рестарт только по marker-файлу «конфиг менялся» |
| Правка в профиле пропала после деплоя | профиль — не источник правды | править дерево, синк разнесёт |
| Дрейф профильных копий между деплоями | агент пишет в свой профиль (это его каталог) | не страшно: синк перезатирает каноном, check ловит |

## 9. Границы модели (что не решается на этом уровне)

- **Межпрофильная изоляция данных.** `/opt/data` общий, uid общий: любой
  агент технически может прочитать `<profile>/.env` чужого профиля. Сделать
  креды «невидимыми» внутри одного контейнера нельзя — можно только убрать
  их из общего пространства (маунты/env), что и делает эта конвенция. При
  жёстких требованиях — разносить профили по отдельным контейнерам
  (изменение стека Hermes, отдельная задача).
- **Маунт кода приложения** (read-only, аналог `FIN_BONDS_ROOT`): код
  читаем всеми профилями; `.env` хоста недоступен (другой uid, mode 600) —
  держать boundary-проверку в диагностике (§7).

## 10. Внедрение в новом проекте (чек-лист с нуля)

1. Заполнить карту окружения (§0).
2. Создать дерево `skills_hermes/<категория>/` + манифест
   (`canonical.skills`), валидатор frontmatter + pre-commit hook.
3. Deploy-скрипт: rsync дерева на хост → копия compose-override → гигиена (§5) →
   `compose up -d` → диагностика (§7) → синк профиля → check.
4. Враппер(ы) доступа к данным (§2.4); env контейнера пустой от секретов.
5. Make-таргеты: `deploy-skills`, `check-skills-profile`.
6. В конфиги Hermes ничего не добавлять из §2.2–2.3 — с первого дня.
